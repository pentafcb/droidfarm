# DEPLOY — manager binderfs self-heal on instance create

## What it is
`manager/app.py` `ensure_binder_devices()` (commit 4928452). Root cause it
fixes: a host reboot drops the binderfs device pool back to the stock set, and
the manager's `free_binder_triplet()` then returns nothing — "Add instance"
fails farm-wide with `no free binder devices` until a human re-creates the
devices by hand (the manual ioctl dance from the 15→20-instance scaling).

Now, when creation finds no free triplet, the manager recreates the pool
(`binder`, `binder1`…`binder63` via `binder-control`, mounting binderfs first
if needed) and retries the triplet lookup once before failing. Device names
are generated internally (no user input) — interpolation-safe.

2026-10-13: on a brand-new host the `binder_linux` kernel module may never
have been loaded at all (this is exactly the new VPS 64.177.49.68, where
every create fails with `no free binder devices`) — then the binderfs mount
itself fails. `ensure_binder_devices()` now best-effort `modprobe
binder_linux` whenever binder-control is missing, before attempting the
mount. No-op when the module is already loaded; a failed modprobe falls
through to the mount with the same outcome as before (no regression).

2026-10-13 (same day): REGRESSION FOUND + FIXED — a `modprobe binder_linux
devices=64` variant shipped briefly and is reverted here. The binder
`devices` module parameter is a comma-separated NAME list (kernel
`CONFIG_ANDROID_BINDER_DEVICES` semantics), NOT a count: a numeric value
creates a single device literally named `64` and zero `/dev/binder*` nodes
— observed on the vultr node, `modprobe binder_linux devices=64` loaded the
module but `ls /dev/binder*` showed nothing. The modprobe call in
`ensure_binder_devices()` therefore passes NO `devices=` argument; the
64-device pool comes from the `binder-control` loop, and the persistent
fresh-install config (`install.sh` → `/etc/modprobe.d/binder.conf`) carries
the explicit name list `binder,binder1,…,binder63` (generated by the marked
`binder-names` block in `install.sh`; modprobe applies modprobe.d options
itself, so the runtime `modprobe` command line also carries no `devices=`).

## Tests
`test_binderfs_selfheal.py` — 36/36 pass (fake `/dev/binderfs` state
transitions, hermetic): full pool → False with zero writes; stock set →
binder26..binder63 created, True; missing binder-control + mount ok → proceeds;
mount fails → False, no creation attempted; creation failure tolerated (False,
no raise); `count` respected; end-to-end no-triplet → ensure → retry yields a
free triplet; names strictly `binder`/`binderN`, no shell metachars;
module missing + modprobe fails → attempted, False, no writes;
module missing + modprobe succeeds → mount proceeds, 64 devices, True;
modprobe never called on the healthy path; REGRESSION: no `devices=` on any
modprobe call or code line in `ensure_binder_devices`; `install.sh` has no
numeric `devices=<n>` in code, no `devices=` on its runtime modprobe line,
and its marked name generator yields exactly the 64 expected names
(`binder`…`binder63`, all valid, all unique).
